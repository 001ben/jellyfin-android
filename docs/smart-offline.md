# Smart offline episode downloads

Open **Downloads > Smart offline** after signing in, or tap **Automatic downloads** on a supported show card/detail page. The full-screen form keeps its Material save button visible, validates fields inline and shows actual scheduler state. Enable the feature, choose 1-20 episodes per series (default 3), choose a permitted connection, then use **Browse shows** or search and select artwork rows. Selected shows remain visible with a stop-selection control and Undo. Series selections save immediately; other settings require the save button. Settings and subscriptions are scoped to the signed-in server and user.

The save bar distinguishes unsaved edits, saving, saved settings and scheduler acceptance. **Check queued** means Android accepted a request, not that it ran. **Check running** is observed from WorkManager; the last worker report is labeled separately. Opening the form only observes local state. Closing with unsaved settings asks whether to discard them. Search results belong to the submitted query; selected series remain visible independently.

Downloads require either an optional verified LAN endpoint or explicit permission to use the configured remote endpoint. Both automatic downloading and watched cleanup start disabled. Unmetered Wi-Fi is required by default. Disabling that option permits other connected networks, including metered/roaming networks. No network or VPN settings are modified.

## Selection, storage and cleanup

The selector orders unwatched episodes by season and episode number, omits duplicates, specials, virtual/missing episodes and future premiere dates, and maintains the next N slots. A manual download already occupying a slot is retained and never adopted for cleanup. Episodes need a known positive media-source size; an unknown-size or oversized episode is skipped rather than downloaded without a budget. This can leave fewer than N episodes available.

The default cap is 10 GiB, configurable from 1–100 GiB. Admission counts every file in this feature's private storage, including partial and retained files and files belonging to other accounts; an account's configured cap can therefore conservatively pause it when another account already uses the space. Each transfer also checks actual response size, bytes written and a 256 MiB disk reserve. Lowering a cap pauses additions until usage falls below it; it does not evict unwatched videos. Manual downloads are outside this budget and cleanup ownership.

**Automatically remove watched managed downloads** is opt-in. A fresh server `Played` state, no pending local playback event and no active playback lease are required. Cleanup deletes only the exact private file recorded by this feature and validates server/user/item/path ownership before removing its download record. It never calls a server media-delete API or traverses the user's chosen download folder. Watched partial files can also be removed. Deselecting stops replenishment and interrupts an in-flight transfer at its next policy check (at most about one second, plus a blocked network read). Existing complete and partial files remain. They still follow the global watched-cleanup setting; deselection never silently disables cleanup. Disable the feature to stop recurring downloads and cleanup.

The standard Downloads delete action works for managed files, respecting active playback and pending synchronization. Choosing to retain a file keeps its ownership record and budget usage. A still-subscribed series may download or register it again on a later pass.

## Browsing and playback integration

Recognized Jellyfin Web 10.11 show cards and episode/show detail pages gain an **Automatic downloads** action. It opens the native manager focused on that show; it does not subscribe or start a download. Episode cards and lists show native queued, transferring, partial, complete and removed status where available. A selected show is labeled **Selected for automatic downloads**, which does not imply the master feature is enabled. Status comes from the current server/user's local records, not a successful worker result alone.

Normal native playback checks for a verified complete local main file before requesting remote playback metadata, including next/previous items in a mixed queue. Missing, incomplete, wrong-account, wrong-media-version and invalid ownership records fall back to the existing remote path for a normal Play action. An explicit **Play downloaded** action requires a usable local copy and reports an error if it disappears. Once local playback is selected, a decoder failure stays visible rather than silently streaming. Local resume and explicit play-from-start/audio/subtitle options are preserved. Embedded tracks and downloaded external text subtitles work in the native player. Existing nonblocking player preference and media-segment requests may still be attempted independently.

External SRT/SubRip, SSA/ASS, WebVTT and TTML tracks for the downloaded media source are fetched as WebVTT from the verified download endpoint. Choose the desired language in the native player subtitle menu; unavailable external tracks are hidden. At most 32 external text tracks of 4 MiB each are saved per episode, within the same managed-storage cap and free-space reserve as video. Conversion preserves text/timing, rather than every ASS styling effect. Bitmap/image subtitle sidecars are unsupported and reported in episode activity; embedded bitmap tracks retain the existing player support.

A permitted check backfills missing subtitle files for existing managed videos without downloading video again. A failed subtitle fetch leaves video playable, shows a separate incomplete/retry message and retries with WorkManager backoff, while allowing other episode videos to finish. Small interrupted subtitle responses restart and are never offered to the player. Local playback accepts only complete, exact-size subtitle records belonging to that download and its canonical managed path; it never follows a cached server subtitle URL. Watched cleanup removes only that managed episode's video and subtitle files, including interrupted subtitle staging files. Deselecting a show stops subtitle backfill as well as new video downloads.

With web or external player preferences, synchronous plugin selection uses a fresh account-bound local-availability cache (15 seconds). Before its first snapshot, the configured player remains selected; **Play downloaded** or native Downloads provides an explicit local route. SyncPlay and casting retain their existing routes. The existing Downloads list is now account scoped and its local actions carry captured account IDs.

The Android repository does not contain the server's web application. Enhancements feature-detect the supported card/list data attributes and classic detail toolbar; custom themes and future web layouts can omit them. Loading browse pages from a cold offline start still requires server/web assets. Use native **Downloads** for offline entry. The new bridge accepts bounded string messages only from the configured top-level web origin, checks current native server/user/token before and after asynchronous work, and exposes no credentials, URLs or file paths. Unsupported WebViews retain the native entry point rather than gaining a broad JavaScript-interface fallback.

The **Episode activity** section separates transfer state from watch state: watched with server sync pending, confirmed cleanup eligibility, watched copies retained, and successful local removals. Cleanup eligibility is display information; deletion repeats every ownership, consent, pending-sync and active-playback check. A bounded history retains the latest successful removal per displayed episode (up to 100 events per account). Missing records or a never-created file cannot produce a removal event. Deselecting retains files and leaves the watched-cleanup policy in effect.

Poster metadata is stored without credential-bearing URLs. Requests capture the specific server/user credentials, use account/item/tag cache keys and reject redirects. Generic opening is cache-only; explicit Browse/Search/context actions may fetch posters and metadata through the already configured server endpoint, never an unverified LAN override. Missing artwork uses a placeholder. Browse displays up to 50 shows; search narrows larger libraries.

## Home LAN routing

Configure the Jellyfin base URL, including any reverse-proxy path, such as `https://jellyfin.home.example/jellyfin`. HTTPS endpoints must have valid TLS trusted by Android and resolve entirely to local addresses over a non-VPN unmetered Wi-Fi network. Embedded credentials, query strings and fragments are rejected. The normal signed-in server address is kept separately and can continue to use Tailscale.

An optional **Trust HTTP for this address** exception supports a literal RFC1918 private IPv4 address with an explicit port. It starts disabled, displays an address-specific warning, and requires **Trust this address** followed by saving. Consent is stored for that exact canonical URL and account; changing the URL clears it. Hostnames, public IPs, Tailscale CGNAT addresses, loopback, link-local and IPv6 are rejected for HTTP. Existing settings migrate without granting HTTP trust.

**HTTP sends the Jellyfin session token and media unencrypted over the selected Wi-Fi network.** A matching public Jellyfin server ID is a consistency check, not cryptographic authentication: a hostile local network can impersonate the server or alter content. Use the exception only if that risk is acceptable. HTTP is never inferred from a failed HTTPS request, and certificate verification is never relaxed.

On initial setup a credential-free public identity request to the existing remote server pins its Jellyfin server ID. Each LAN pass probes `/System/Info/Public` without credentials and requires the same ID before authenticated requests. HTTPS also verifies TLS; trusted HTTP retains the risk described above. DNS results are held for that pass; HTTP additionally requires the resolved numeric address to match the explicitly approved address. Media and selection metadata use that Wi-Fi network's socket factory and DNS, bypassing proxies without changing system routing. Redirects and TLS downgrades are disabled. If the LAN probe fails, the configured remote endpoint is used only when **Allow downloads through the configured remote endpoint** is selected; its existing transport/VPN route is retained.

With trusted HTTP, playback progress writes and the fresh watched-state confirmation required for cleanup stay on the normal server connection. If that connection is unavailable, cleanup is deferred and the watch outbox remains pending, while reachable HTTP LAN downloads can continue. HTTP responses cannot alone authorize watched-file deletion.

Wi-Fi-only remote fallback additionally checks the active route's Wi-Fi/unmetered capabilities. A spare connected Wi-Fi network cannot authorize cellular traffic. VPN implementations that do not expose their Wi-Fi underlay conservatively wait. VPN lockdown may prevent direct LAN sockets; the app respects that restriction. SSIDs, location access and live server credentials are not required to configure the feature's code.

## Scheduling and recovery

Unique WorkManager jobs are requested when saved, after offline playback synchronization, and approximately hourly. Android may defer them for Doze, battery restrictions, missing network constraints or job quotas. The screen observes queued, running, retry and terminal states without starting a check itself. They require storage-not-low, use exponential retry backoff and show a cancellable foreground download notification. Each pass is bounded to eight minutes; subsequent passes resume safely. Cancel stops the current pass; disable the feature to stop recurrence. Android 16 foreground-worker quotas can delay further work.

Partial video bytes and strong ETags are durable. Resumes use `Range` plus `If-Range`; changed content restarts from zero, invalid range/validator responses invalidate the resume validator, and a matching HTTP 416 can recover a completed file after a process death. Servers without a strong ETag restart interrupted files. Short bodies never become playable download records. Partial progress is visible in the smart catalog, but files become playable Downloads records only after a verified complete transfer. Video is downloaded directly without transcoding; external text subtitles are converted by Jellyfin to WebVTT and stored separately.

Local playback snapshots are serialized and ordered when captured. The durable outbox includes server/user/item identity, survives outages and manual removal, and never discards watched state after an arbitrary retry count. Acknowledgements delete only the sent revision. Successful stop reporting is remembered separately from marking a fully finished episode played. Partial stops leave watched-state decisions to Jellyfin; the client never explicitly unmarks an episode. Pending local finishes are excluded from replenishment selection while cleanup waits for server confirmation. Resume position is saved locally. A separate hourly connected-network job recovers pending synchronization after app/process restart.

This is an independent implementation informed by the approach in [PR 2169](https://github.com/jellyfin/jellyfin-android/pull/2169), not a merge or cherry-pick of that unmerged proposal. A separate Room database avoids changing the existing download schema and keeps later reconciliation with that PR possible.

## Build and install yourself

Use JDK 21, the repository Gradle wrapper and the Android SDK required by `gradle/libs.versions.toml`:

```powershell
.\gradlew.bat :app:testLibreDebugUnitTest :app:lintLibreDebug :app:assembleLibreDebug
```

Find the APK under `app/build/outputs/apk/libre/debug/`. The debug application ID is `org.jellyfin.mobile.debug`, so it can coexist with the official release. Copy the APK to the phone and open it, granting installation permission to your chosen file manager if requested. Alternatively, run `adb install -r <path-to-apk>` yourself on your authorized device. Future debug updates need the same signing key. Install only on an explicitly selected authorized device. Building and preparing this integration update does not install it on a phone.

Unit tests use temporary files and local HTTP/HTTPS fixtures, never a live server. They cover ordered selection/replenishment, cleanup gates and ownership, storage limits, interrupted/changed transfers, retries, playback ordering, LAN identity/TLS/redirect/fallback policy, and metadata through a verified LAN route. An isolated emulator also plays a generated local H.264 fixture through Media3 with remote resolution unavailable. Physical-device scheduling, VPN-underlay behavior, real-server browsing and playback with real media still require device testing.

For isolated emulator UI tests, build both APKs with `-PuiTests=true`. This includes an empty Compose test host only in that test build; ordinary debug APKs do not package it. Instrumentation tests use fake accounts and callbacks plus a generated local media fixture, never live credentials, background scheduling or server media. Room tests validate additive v1-to-v3 and v2-to-v3 migration, preserving HTTP consent, ownership, partial data and pending playback revisions. Local WebView fixtures render supported classic/React-shaped layouts and exercise genuine touches without contacting a server. Target a specific emulator serial when installing/running tests; do not run connected tests indiscriminately while a user's phone is attached.
